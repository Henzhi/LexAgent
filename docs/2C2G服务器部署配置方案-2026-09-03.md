# 2C2G 服务器部署配置方案（2026-09-03）

> 背景：用户希望支持"多开对话、同时提问、同时生成"。服务器为 **2 CPU / 2GB 内存**。
> 本文给出三套可行部署配置的**完整改动清单 + 预期资源账 + 代价**，供评审后落地。
> 只列出需要改的文件与改动内容，不含已就绪部分。

## 0. 先说清：生成不占你 2C2G，检索才占

- LLM 主路径 = **DeepSeek API**（外呼，服务器只做 SSE 转发），多开对话的增量成本 = 每路一个长连接（内存开销极小）+ API 预算（F14 熔断全局兜底）。
- 真正吃 2C2G 的是**检索链路本地资源**，分三类：

| 吃资源项 | 载体 | 常驻内存 | 并发时行为 |
| :--- | :--- | :--- | :--- |
| **Reranker**（bge-reranker-v2-m3） | **app 进程内**（sentence-transformers/torch，不走 Ollama） | ~1.2–2GB fp32 | 每查询 15 对 cross-encoder CPU 推理 0.5–2s，**CPU 排队** |
| **Embedding**（bge-m3） | Ollama（宿主机 / 另一台） | ~1.2GB fp16 | 向量化查询，Ollama 串行 |
| **降级 LLM**（qwen2.5:3b） | Ollama | ~2GB Q4 | 仅主后端故障时启用 |

2C2G 可用内存约 1.8GB。PG(~300MB) + Redis(~150MB) + app(~300MB) ≈ **0.75GB 已固定**。
剩余 ~1GB：reranker 塞不下、bge-m3 + 3b 降级也塞不下 → **不取舍必 OOM，容器随机被杀**。

---

## 路线 A：瘦身全栈（推荐，余量最足）

**目标形态**：2C2G 只跑 pg + redis + app；检索 embedding 走 OpenAI 兼容 API；rerank 关闭或换小模型；降级后端不跑 Ollama LLM。

### A1. `.env`（宿主机，compose 读取）

```dotenv
# ---- LLM ----
LLM_BACKEND=openai
OPENAI_API_KEY=sk-xxxx                        # DeepSeek key（OpenAI 兼容）
OPENAI_BASE_URL=https://api.deepseek.com/v1
OPENAI_MODEL=deepseek-v4-flash

# ---- Embedding 迁 API ----
EMBED_BACKEND=openai
OPENAI_EMBED_MODEL=text-embedding-3-small     # OpenAIEmbedder 已支持
# 若用国内兼容 embedding（如 siliconflow/百炼），再加：
# OPENAI_BASE_URL 已在上面指向 DeepSeek——embedding 与 chat 必须同 base_url 时，
# 请换一家同时提供两者的 OpenAI 兼容网关，或拆开单独配 EMBED_BASE_URL_OVERRIDE（见 A-备注）

# ---- Rerank：关（最省）或换小模型（保质量）----
RERANK_ENABLED=false
# 若想保留精排但压内存，改小模型并在 requirements 增装：
# RERANK_ENABLED=true
# RERANK_MODEL=BAAI/bge-reranker-base        # ~0.4GB，质量略降
# RERANK_RECALL_K=15
# RERANK_TOP_K=5

# ---- 并发（多开上限）----
LLM_MAX_CONCURRENCY=4

# ---- PG 池（2C2G 收紧，防连接风暴占满内存）----
PG_POOL_MINCONN=1
PG_POOL_MAXCONN=8
```

> ⚠️ **compose 部署必须同时改 A2**：`docker-compose.yml` 的 `app.environment` 是**白名单制**（容器没有 `env_file`，只有显式列出的变量才注入，且 `RERANK_ENABLED=true` 在 compose 里是**硬编码**）。仅改 `.env` 不会生效——`.env` 只参与 `${VAR}` 插值，未列入 `environment` 的键不会进容器。**裸跑 uvicorn**（非 compose）才可只改 `.env`。

### A2. docker-compose.yml（compose 部署必改）

把 `app.environment` 段中两处硬编码/缺失改为透传：

```yaml
      # 原：- RERANK_ENABLED=true           → 改为变量透传
      - RERANK_ENABLED=${RERANK_ENABLED:-false}
      # 新增：embedding 后端与并发透传（白名单制，不加不生效）
      - EMBED_BACKEND=${EMBED_BACKEND:-ollama}
      - OPENAI_API_KEY=${OPENAI_API_KEY:-}
      - OPENAI_BASE_URL=${OPENAI_BASE_URL:-}
      - OPENAI_EMBED_MODEL=${OPENAI_EMBED_MODEL:-text-embedding-3-small}
      - LLM_MAX_CONCURRENCY=${LLM_MAX_CONCURRENCY:-4}
      - PG_POOL_MINCONN=${PG_POOL_MINCONN:-1}
      - PG_POOL_MAXCONN=${PG_POOL_MAXCONN:-8}
```

（其余 PG/Redis/FAQ 段不动；`host.docker.internal` 的 Ollama 引用保留但不再使用。若走 SiliconFlow 网关，把 `OPENAI_MODEL=${OPENAI_MODEL:-deepseek-v4-flash}` 的默认值对应替换。）

### A3. 预期

| 项 | 值 |
| :--- | :--- |
| 常驻内存 | PG 0.3 + Redis 0.15 + app 0.3 ≈ **0.75GB**，余 ~1GB 给 OS/buffer |
| 多开并发 | `LLM_MAX_CONCURRENCY=4`，4 路 SSE 并行流畅；想更高改 8 亦可 |
| rerank 关闭的代价 | 精排降一档；由 BM25+向量双路 RRF + ArticleRouter 粗排兜底（multi100/colloq148 需跑一次离线对比确认掉点幅度） |
| 失败风险 | embedding API 故障 = 检索不可用（建议网关选 SLA 高的；retry=3 已有） |

## 路线 B：保留本地 Ollama 检索（质量优先，压并发）

**目标形态**：Ollama 仍在本机跑 embedding（+可选降级 LLM）；**关 rerank**（内存装不下）或换 bge-reranker-base；并发压到 2–3。

### B1. `.env`

```dotenv
LLM_BACKEND=openai
OPENAI_API_KEY=sk-xxxx
OPENAI_BASE_URL=https://api.deepseek.com/v1
OPENAI_MODEL=deepseek-v4-flash
LLM_FALLBACK_BACKEND=ollama
LLM_FALLBACK_MODEL=qwen2.5:3b               # 或干脆不配 fallback，降级=报错

EMBED_BACKEND=ollama
EMBED_MODEL=bge-m3                          # 建议换更小的：bge-small-zh / nomic-embed-text（~0.1–0.3GB）
EMBED_BASE_URL=http://127.0.0.1:11434

RERANK_ENABLED=false                        # 2C2G 装不下 1.2GB+ 进程内 reranker
# 或：RERANK_ENABLED=true + RERANK_MODEL=BAAI/bge-reranker-base + RERANK_TOP_K=5

LLM_MAX_CONCURRENCY=2                       # 检索走本地 Ollama，CPU 串行，压并发保延迟
```

### B2. Ollama 侧（宿主机，非 compose）

> ⚠️ compose 部署同样先按 A2 加白名单透传（`EMBED_BACKEND`/`EMBED_MODEL` 已有 `EMBED_MODEL=${EMBED_MODEL:-bge-m3}` 透传，但 **`EMBED_BACKEND` 未透传**且 `RERANK_ENABLED=true` 硬编码——B 路线要把这两行改成变量/`false`）；`EMBED_BASE_URL` 已有透传（指向 11434 默认）。裸跑 uvicorn 无此问题。

```bash
# 模型量化/选型
ollama pull bge-m3            # 或 bge-small-zh-v1.5 更省
# Ollama 服务并行度=1，避免同机多查询争 CPU
systemctl set-environment OLLAMA_NUM_PARALLEL=1
systemctl set-environment OLLAMA_MAX_LOADED_MODELS=1
systemctl set-environment OLLAMA_KEEP_ALIVE=5m   # 空闲 5 分钟卸载，省常驻
systemctl restart ollama
```

### B3. 预期

| 项 | 值 |
| :--- | :--- |
| 常驻内存 | 0.75GB(app 栈) + Ollama bge-m3 ~1.2GB ≈ **~2GB 顶格**（量化/小模型后 ~1.3GB 才安全） |
| 多开并发 | **2–3 路**（受 Ollama embedding CPU 推理限制）；超过则排队、延迟变长 |
| 代价 | 多路并行时每路延迟明显上升；Ollama 与 app 抢 CPU |

⚠️ B 路线在 2C2G 上偏紧，建议 **bge-m3 → bge-small-zh-v1.5** 并把 embedding batch=1，否则多开时内存仍危险。

## 路线 C：拆两台（容量最大，多一台机器）

**目标形态**：2C2G 只跑 pg + redis + app（重量级推理全外移）；Ollama（embedding + rerank + 降级 LLM）放另一台机器（或本地 VM，你已有 Docker VM 承载姊妹项目）。

### C1. `.env` / compose

```dotenv
# app 侧与路线 A 相同：EMBED_BACKEND=ollama 也行（指向远程 Ollama）
EMBED_BACKEND=ollama
EMBED_BASE_URL=http://<OLLAMA_HOST_IP>:11434   # 指向另一台机器

RERANK_ENABLED=true                             # rerank 在 app 进程内！仍吃 2C2G → 必须 false
# ⚠️ reranker 是进程内 torch 模型，无法"指到远程"；想保留 rerank 得：
#   方案 C1：rerank 也跑在 Ollama 机——需把 rerank 从 sentence-transformers 迁移为
#   Ollama 上的 cross-encoder 服务（如 rerank 模型走 Ollama 需新增对接代码，列为工作量项）
#   方案 C2（0 代码）：RERANK_ENABLED=false，检索只靠 embedding 双路

LLM_MAX_CONCURRENCY=6
```

compose `app.environment` 的 `OLLAMA_URL`/`EMBED_BASE_URL` 改成远程 IP（去掉 `host.docker.internal` 假设），并按 A2 加 `EMBED_BACKEND`/`RERANK_ENABLED`/`LLM_MAX_CONCURRENCY` 白名单透传；`EMBED_BASE_URL=${EMBED_BASE_URL:-http://host.docker.internal:11434}` 改为 `${EMBED_BASE_URL:-http://<OLLAMA_HOST_IP>:11434}`。

### C2. 预期

| 项 | 值 |
| :--- | :--- |
| 2C2G 常驻 | ~0.75GB，余量充足 |
| 多开并发 | 6–8 路无压力；极限受 API 预算与 Ollama 机性能 |
| 代价 | 多维护一台机器；rerank 若保留需迁移实现（工作量大） |

## 决策表

| 你的优先级 | 选 | 一句话 |
| :--- | :--- | :--- |
| 单机最省事、要流畅多开 | **A** | embedding 迁 API + 关 rerank，代码零改动 |
| 检索质量优先、能接受低并发 | B | 本地 bge-small + 关 rerank + 并发 2 |
| 已有/愿意加一台机器 | C | 2C2G 瘦身只跑主栈，Ollama 外移 |

## 落地前必做验证（任何路线）

1. **内存观测**：`docker stats --no-stream`，确认 RSS < 1.6GB 且 24h 无 OOM（`dmesg | grep -i oom`）。
2. **并发冒烟**：同一时间开 2/4 路提问，看 P95 首 token 延迟是否可接受（目标 <3s）。
3. **质量回归（关 rerank 或换小模型后必跑）**：
   ```bash
   uv run python scripts/run_retrieval_eval.py --benchmark multi100   # 与 RERANK_ENABLED=true 基线对比
   uv run python scripts/run_retrieval_eval.py --benchmark colloq148
   ```
   掉点 <5% 可接受；掉点多则退回 B 或补 rerank 小模型。
