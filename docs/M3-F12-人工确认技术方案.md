## 0. 结论摘要（TL;DR）

| 问题 | 结论 |
| :--- | :--- |
| human-in-the-loop 技术上可行吗？ | ✅ 可行。LangGraph 1.2.8 的 `interrupt()` + `Command(resume=...)` 挂起-恢复全链路验证通过 |
| 必须动图执行架构吗？ | ❌ **不必**。v1 用「进入图之前前置确认」，图结构零改动 |
| v1 需要 checkpointer 吗？ | ❌ **不需要** |
| v1 需要新增依赖吗？ | ❌ **不需要** |
| 两种确认粒度成本差多少？ | 约 **1 : 4**（v1 前置确认 ≈ 2 人日，v2 逐步骤 ≈ 6-7 人日） |
| 给 Q5 的建议 | **v1 选「整个场景一次确认」** |

**最重要的发现**：原本判断 F12 是「M3 里唯一会动到执行架构的改动」，spike 后这个判断被推翻——
只要确认点放在**进入 ReAct 循环之前**，「整个场景确认」根本不需要 `interrupt`，
因为此时图还没开始执行，只需要一个前置分支 + 一个「已确认」标记即可。

这条路径完全不触碰 D-M3-1 的红线（禁止手写循环步进节点、状态合并必须走 reducer）。

> **✅ 决策结果（2026-08-29）：走路径 A 一次确认**（D-M3-9a），与本文 §4 推荐一致。
>
> 过程中一度倾向路径 B（希望用户看到中间结果再决策），澄清后确认：
> **「断线重连继续生成」是独立的 SSE 可靠性需求，与确认粒度正交**，
> 不随路径 A/B 的选择而丢失，方案见 D-M3-12。
>
> **结论：checkpointer 与 `interrupt()` 本期均不引入**，无需新增任何依赖。
> 本文 §3.3 路径 B 的分析、§5 风险清单保留，作为将来若确实需要
> 「看到中间结果再决策」时的备选资料。

## 2. Spike 验证结果

验证脚本：`scripts/f12_spike_demo.py`（不依赖真实 LLM / 网络 / API Key）

```

```

因此结论可直接迁移到真实代码。

| # | 验证项 | 结果 |
| :--- | :--- | :--- |
| 1 | B 类场景：interrupt 挂起 → `Command(resume=True)` 恢复 → 出答案 | ✅ |
| 2 | 无 checkpointer 时的失效模式 | ✅ 确认为硬依赖（且失效极隐蔽，见 §5 R1） |
| 3 | A 类场景不触发确认（回归保障） | ✅ 零挂起、正常出答案 |
| 4 | `thread_id` 隔离（多会话并发安全） | ✅ 两 thread 状态互不覆盖 |
| 5 | 用户拒绝（`resume=False`） | ✅ 图继续跑完，不卡死 |

**验证 1 的关键产出**（证明挂起-恢复不破坏消息配对关系）：

```
第一次调用 → 节点 agent 产出 tool_calls → ⏸ 挂起（状态已持久化，messages=2 条）
第二次调用（resume=True）→ confirm → tools → agent → 出答案
messages 轨迹：['human', 'ai', 'tool', 'ai']
✅ 4 条完整，含 assistant(tool_calls) —— 挂起/恢复未破坏 add_messages 配对关系
```

这一条尤其重要：D-M3-1 那个历史 Bug 的根因就是消息配对被破坏导致 DeepSeek 400。
spike 证明走框架原生 `interrupt` 不会重蹈覆辙——因为它根本不手工合并状态。

## 3. 六问逐条回答

### 3.1 checkpointer 接入成本：MemorySaver vs PostgresSaver

| 方案 | 依赖 | 持久性 | 跨进程 | 成本 |
| :--- | :--- | :--- | :--- | :--- |
| `MemorySaver`（进程内） | ✅ 已有（langgraph-checkpoint 4.1.1） | ❌ 进程重启即丢 | ❌ | 极低（一行） |
| `PostgresSaver` | ❌ 需装 `langgraph-checkpoint-postgres` | ✅ | ✅ | 中（新依赖 + 建表 + 连接池） |
| 自研 Redis checkpointer | ✅ 已有 Redis | ✅ | ✅ | 高（需实现 Checkpointer 协议，~150 行） |

**结论**：
- 当前**单进程部署**（`Dockerfile:30`），`MemorySaver` 可用，但**进程重启会丢全部挂起状态**。
- 若 v2 需要持久化，推荐 `PostgresSaver`：项目已有 PostgreSQL，且 F14 熔断已验证过存储降级思路可复用。
  代价是新增一个依赖（它用 psycopg3，与现有 `psycopg2-binary` 并存）。
- **v1 不需要 checkpointer**（见 §3.3），此问在 v1 阶段不阻塞。

### 3.2 thread_id 从哪来

**已有现成答案**：`ChatRequest.session_id`（`src/api/models.py:14`）。

```
thread_id = f"{user_id}:{session_id}"
```

spike 验证 4 已确认该格式可正确隔离不同会话。
额外好处：`session_id` 由前端持久化，前端刷新后仍可拿到同一个 thread_id——这正好回答了 Q7 的会话恢复问题。

注意：`/api/chat/stream` 目前免认证，`user_id` 可能为空，此时退化为 `f"anon:{session_id}"`，
需在实现时明确空 `user_id` 的处理（涉及隔离粒度，建议一并进 Q7）。

### 3.3 中断点怎么表达：interrupt() vs 自定义节点 + 条件边

**这是本次 spike 最关键的结论——两个粒度对应两种完全不同的技术路径。**

#### 路径 A：整个场景一次确认 → **不需要 interrupt**

确认点放在**进入图之前**（`stream()` 中调用 `graph.stream()` 之前）：

```
POST /api/chat/stream
  → 意图识别 → 场景分类（F11）
  → 是 B 类？
      是 → 查「已确认」标记（Redis）
          未确认 → 产出 confirmation_required 事件 → 结束流（[DONE]）
          已确认 → 继续（正常走完整流程）
      否 → 继续（A 类全自动）
```

为什么不需要 `interrupt`：**此时图还没开始执行，没有任何状态需要保存和恢复。**
只需要一个「本会话已确认」的标记即可。

**成本极低**：
- 图结构改动：**0**（`_graph` 与 `_react_loop_graph` 一行不改）
- 新增依赖：**0**
- 不触碰 D-M3-1 红线（状态合并仍完全由 reducer 负责）
- 恢复时是「重新跑一遍」而非「断点续跑」，但因为确认发生在任何 LLM 调用之前，**零浪费**

#### 路径 B：逐步骤确认 → 必须用 interrupt + checkpointer

确认点在图内部（ReAct 循环中途），此时已有 LLM 调用与工具结果，
必须保存完整状态、第二次请求从断点续跑：

- 新增 `confirm` 节点 + 条件边，且**两个图都要改**（`_graph` 和 `_react_loop_graph`，D-M3-2 双图并存）
- 接入 checkpointer（见 §3.1）
- `interrupt()` 的返回值由业务层解释（spike 验证 5 证明框架只负责传值，不做语义判断）

**成本约为路径 A 的 4 倍**（详见 §4）。

### 3.4 SSE 挂起-恢复：现有事件流怎么改

现有事件类型：`thinking` / `token` / `meta` / `tool_call` / `tool_result` / `FAQ` / `clear` / `error`。

**路径 A 下的改动（v1）**：新增 1 个事件类型

```python
{
    "type": "confirmation_required",
    "scene": "contract_draft",        # F11 场景 id
    "prompt": "即将为「XXX」生成合同草稿，确认生成范围？",
    "options": ["确认", "取消"],       # 由 F11 场景配置驱动
    "confirm_id": "...",              # 供前端回传
}
```

新增 1 个接口：`POST /api/chat/confirm`（带 `confirm_id` + 用户选择 + 可选参数）。

前端确认后**重新发起** `/api/chat/stream`（同一 `session_id`），服务端查到「已确认」标记即正常执行。

**路径 B 下的改动（v2，更复杂）**：
- 第一次流结束于 `confirmation_required`，但底层图处于**挂起态**（不是结束）
- 第二次请求用 `Command(resume=...)` 恢复，只产出**恢复后的事件**
- 前端要把两次流拼成同一条消息 → 前端状态机复杂度显著上升

### 3.5 前端刷新 / 断线后如何恢复（对应 Q7）

**路径 A 天然支持**：「已确认」标记存在 Redis，与前端连接状态无关。
前端刷新后重新加载会话，若发现有待确认请求，重新渲染确认卡片即可，
用户点确认后照常发起新的 stream 请求。

**路径 B 依赖 checkpointer 持久化**：`MemorySaver` 下进程重启即丢，必须上 `PostgresSaver` 才算真正可靠。

### 3.6 两种粒度的成本对比

| 工作项 | 路径 A（整个场景一次确认） | 路径 B（逐步骤确认） |
| :--- | :--- | :--- |
| 场景分类（F11） | 需要（独立事项） | 需要（独立事项） |
| 图结构改动 | **0** | 2 张图各加节点 + 条件边 |
| checkpointer | **不需要** | 需要（选型 + 接入 + 降级） |
| 新增依赖 | **0** | 1（PostgresSaver）或自研 Redis 版 |
| 新接口 | 1（`/chat/confirm`） | 1（`/chat/confirm`） |
| SSE 事件 | +1 类型 | +1 类型，且需两次流拼接 |
| 前端 | 确认卡片 + 重新发起请求 | 确认卡片 + 两次流拼接的状态机 |
| 过期清理 | Redis TTL（天然支持） | 需自行实现挂起态清理 |
| 降级处理 | 标记存储失败 → 回落 A 类 | checkpointer 不可用 → **B 类静默死掉**（§5 R1） |
| 单测 | 常规 mock | 需 fake checkpointer 模拟挂起-恢复 |
| **后端工作量** | **~1 人日** | **~4-5 人日** |
| **前端工作量** | **~1 人日** | **~2 人日** |
| **合计** | **~2 人日** | **~6-7 人日** |

## 4. 推荐方案

### v1：路径 A（整个场景一次确认，前置确认）

**理由**：
1. 成本约为路径 B 的 1/4
2. **完全不触碰图执行架构**，零回归风险（不违反 D-M3-1）
3. 零新增依赖
4. 天然支持会话恢复（Q7）
5. PRD REQ-S1 要求「确认等待状态下不继续执行后续节点」——前置确认天然满足

**实施步骤**：
1. 先完成 F11 场景分类（事项 `rpuMIf`）——这是硬前置
2. 确认标记存储：Redis，`key = lexagent:confirm:{user_id}:{session_id}`，带 TTL（对应 Q7 超时）
3. `stream()` 中在场景分类后插入前置分支（产出 `confirmation_required` 并结束流）
4. `POST /api/chat/confirm` 接口
5. 前端确认卡片
6. 单测：A 类不受影响、B 类未确认则中断、确认后正常执行、标记存储失败回落 A 类

### v2（待定）：路径 B（逐步骤确认）

**触发条件**：产品验证用户确实需要在**生成过程中**干预（例如"检索到 3 个类案，要我用哪几个？"）。
届时再立项，届时决策 checkpointer 选型。

## 5. 风险清单

| # | 风险 | 等级 | 应对 |
| :--- | :--- | :--- | :--- |
| R1 | **checkpointer 静默失效**（spike 验证 2 实证）：无 checkpointer 时 `interrupt` 不报错，图静默停住、answer 为空，前端只收到挂起事件后永远等不到结果，后端日志**无任何异常** | 高（仅路径 B） | 图构建处加启动自检：启用中断时断言 `checkpointer is not None`，否则拒绝启动 |
| R2 | `MemorySaver` 进程重启丢状态（仅路径 B，当前单进程部署） | 中 | v2 若做逐步骤确认，直接上 `PostgresSaver` |
| R3 | **双图并存（D-M3-2）改一处漏一处**：`_graph` 与 `_react_loop_graph` 需同步改造 | 中（仅路径 B） | 抽公共的 confirm 节点 + 条件函数，两图复用（与 D-M3-2 已有的节点字典复用思路一致） |
| R4 | 前端两次流拼接的状态机复杂度（仅路径 B） | 中 | v1 规避；v2 需前端专项设计 |
| R5 | 挂起期间的 cancel / 断开：现有 watchdog（routes.py:556）只处理单次流 | 低 | v1 下第二次流是全新请求，现有机制已能覆盖 |
| R6 | 同一 session 并发发起两个请求导致确认标记竞态 | 低 | Redis `SET NX` + TTL 原子写入 |
| R7 | 确认后用户又改了问题（query 与确认时不一致） | 低 | 标记中存 query 摘要，不匹配则重新确认 |
| R8 | **B 类场景分类错误导致该确认没确认**（F11 准确率问题） | 中 | 依赖 F11 的准确率；未匹配时的回落策略必须保守（F11 事项已定为回落 A 类） |

## 6. 给 Q5 / Q7 的决策建议

### Q5（确认粒度与文案）

**建议 v1 选「整个场景一次确认」（路径 A）**，理由见 §4。

补充两点供产品判断：
1. 「确认」可以是**带参数的**（例如确认时选择审查范围/合同类型），
   spike 验证 5 证明框架只负责传值，参数语义完全由业务层解释——路径 A 同样支持，
   把用户填的参数存进确认标记即可。**这一点不影响粒度选择**。
2. 如果产品判断「用户需要在看到中间结果后再决定」，
   那才真正需要路径 B——因为路径 A 的确认发生在任何检索/生成之前，用户看不到中间信息。
   **这是两种粒度唯一的本质差异**，建议产品按此判断。

### Q7（超时与恢复策略，本次新增）

| 子问题 | 建议 |
| :--- | :--- |
| 超时时长 | **10 分钟**。v1 用 Redis TTL 实现，零额外成本 |
| 超时后的行为 | **取消并提示用户重新发起**。⚠️ **不建议**自动按默认参数继续执行——B 类多为文书/合同/报告，擅自替用户决定存在法律责任风险 |
| 会话恢复 | v1 天然支持：标记在 Redis，前端刷新后重新加载即可重新渲染确认卡片 |
| `user_id` 为空时 | `/api/chat/stream` 当前免认证，需明确隔离粒度（建议按 `session_id` 隔离，并在 Q7 中一并确认） |
