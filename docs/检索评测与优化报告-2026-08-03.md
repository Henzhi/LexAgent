**日期**: 2026-08-03

## 1. 背景

系统自 7 月底完成纯 PG 架构迁移（FAISS → pgvector）、存量重切分（段落级 → 按「第X条」，chunks 15029 → 51348）后，一直缺少对新架构下**检索质量**的量化验证。本次以评测驱动，完成了完整的"找评测集 → 测基线 → 归因 → 修复 → 再测"闭环。

## 2. LexEval 基准适配性分析

### 2.1 尝试过程
下载了 LexEval 六个代表性任务（`1_1` 记忆、`2_1` 理解、`3_1` 推理、`4_1` 辨别、`5_3` 翻译、`6_1` 伦理），编写 `evaluation/scripts/lexeval_eval.py` 通过 `/api/chat/stream` 流式接口批量问答，试点 10 题。

### 2.2 试点结果
- 整体准确率 **20%**（2/10），检索命中率 80%
- 1_1 记忆 0/2、2_1 理解 1/2、3_1 推理 0/2、4_1 辨别 0/2、6_1 伦理 1/2

### 2.3 结论：评测目标错位，不适用本系统
LexEval 是 **LLM 能力基准**（NeurIPS 2024，测模型自身法律知识/推理/生成），而本系统是 **RAG 检索增强系统**：
1. 知识来源不同：LexEval 覆盖全法律领域，知识库仅 931 篇文档，检索不到就退化为"3b 裸答"
2. 检索可能帮倒忙：检索到不相关条文时，prompt 强制"基于材料回答"会带偏模型
3. 试点数据印证：检索命中 80% 但准确率 20%，瓶颈在模型与知识覆盖，不是检索

**结论**: 不再全量跑 LexEval，改用项目自建、针对知识库定制的评测集。

## 3. 项目自建评测集（最适合本系统的测试集）

`evaluation/data/eval_queries.json`（100 条）：`{query, relevant: [{law_name, article_number}]}`，每条问题标注"应召回哪部法哪一条"，直接测 RAG 命门——检索命中率（Hit@k / MRR）。

评测脚本 `evaluation/scripts/eval_retrieval.py`：
```
uv run python evaluation/scripts/eval_retrieval.py              # 生产配置评测
uv run python evaluation/scripts/eval_retrieval.py --bare       # 纯向量消融
uv run python evaluation/scripts/eval_retrieval.py --queries evaluation/data/eval_queries_articles.json   # 自定义评测集
```
输出 UTF-8 报告到 `evaluation/data/lexeval/results/retrieval_{prod,bare}.txt` + 逐条明细 JSONL。

## 4. 检索质量归因分析

### 4.1 基线对比（重切分后，未优化）

| 指标 | 重切分后 PROD | 旧 FAISS 基线 | 差值 |
|---|---|---|---|
| Hit@1 | 34.0% | 52.0% | -18.0% |
| Hit@3 | 53.0% | 65.0% | -12.0% |
| Hit@5 | 64.0% | 73.0% | -9.0% |
| Hit@10 | 67.0% | 81.0% | -14.0% |
| MRR | 0.4541 | 0.6113 | -0.1572 |

### 4.2 根因一：article_map.json 缺失（相邻扩展空转）
存量重切分直写数据库，未触发入库时的 `article_map.json` 增量更新，导致生产配置中 `AdjacentExpander` 加载 0 部法律（空转）。
**修复**: 新建 `scripts/rebuild_article_map.py` 从 DB 全量重建，覆盖 **887 部法律 / 44749 条条文**。

### 4.3 根因二：按条切分后 chunk 正文不含法名
抽样验证：97% 的 article chunk 内容仅"第X条 + 正文"，**法名只在 metadata**。导致：
- "法名+条款号"查询（如"刑法第二十条"）被其他法律同号条文抢占，目标条文丢失（top-8 全是别法的"第二十条"）
- 这是重切分导致召回下降的主因

### 4.4 ADJACENT_WINDOW 3→1 的影响验证（改 .env 实测）
| 配置 | Hit@1 | Hit@3 | Hit@5 | Hit@10 | MRR |
|---|---|---|---|---|---|
| ADJACENT_WINDOW=1 | 39.0% | 58.0% | 69.0% | 72.0% | 0.506 |
| ADJACENT_WINDOW=3 | 39.0% | 58.0% | 69.0% | 72.0% | 0.506 |

**结论**: 窗口大小对召回指标无影响（相邻扩展只对已命中条文补邻居，救不回未命中的目标条文）；但 window=3 会把大量"相邻但不相关"条文塞进 prompt（引用噪声），改回 1 是正确优化。

### 4.5 未命中归因（37 条 Hit@5 未命中）
- **法名+条款号查询**: 5 条（纯向量结构性缺陷，法名不进 chunk 正文）
- **法名进 top-15 但条号不中**: 24 条（目标条文被同法其他短条文挤占）
- **法名未进 top-15**: 8 条（纯语义失败）

## 5. 修复一：条款号精确路由（ArticleRouter）

### 5.1 实现
新增 `src/rag/article_router.py`（装饰器，置于检索链最外层）：
- 解析查询中的"第X条"（中文数字 → 整数）
- 提取法名线索（《书名号》优先，其次"X法/条例/规定"后缀词）
- 从 DB 精确查 `metadata->>'law_name' LIKE %法名% AND article_range 含该条款`
- 精确命中置顶，再拼基础检索结果（去重）

接入 `src/api/dependencies.py`，所有检索入口（engine/agent）自动生效。

| Hit@3 | 53.0% | 58.0% | +5.0% |
| Hit@5 | 64.0% | 69.0% | +5.0% |
| Hit@10 | 67.0% | 72.0% | +5.0% |

## 7. 修复二：条件 BM25 rank-based 混合检索

### 7.1 设计（对齐"BM25 按返回顺序、与向量精确检索逻辑不同"）
- **rank-based 融合**: 加权 RRF，`fusion = Σ w/(k + rank)`，只看排名不碰分数
- **法名入 BM25 索引**: 索引文本 = `法名 + 条文正文`（向量做不到的法名精确匹配，BM25 能）
- **条件激活**: 查询含 `第X条` / `《法名》` / `X法·条例·规定` 后缀词时 BM25 才参与，否则纯向量零干扰
- **懒加载**: BM25 索引（51348 chunks）首次激活查询时构建（约 50s），启动无负担

新增: `src/rag/bm25_retriever.py`（jieba 分词 + rank-bm25）、`src/rag/hybrid_retriever.py`

### 7.2 权重寻优（法条级测试集）

| 配置 | Hit@1 | Hit@3 | Hit@5 | Hit@10 |
|---|---|---|---|---|
| 纯向量 | 62.8% | 69.3% | 75.8% | 82.0% |
| 混合 w=0.5 | 64.9% | 76.4% | 82.0% | 88.5% |
| 混合 w=1.0 | 65.5% | 79.1% | 83.2% | 91.7% |
| 混合 w=2.0 | 67.3% | 79.1% | 85.5% | 91.4% |

## 9. 遗留与后续建议

1. **法条级测试集可扩展**: 当前 339 条（60 部法律抽样），可加 `--max-laws`/`--per-law` 放大；关键词提取可进一步用 TF-IDF 增强
2. **BM25 索引持久化**: 当前懒加载每次进程重启重建（约 50s），可序列化缓存到磁盘加速
3. **通用语义查询的"法内聚焦"**: 语义集 31 条未命中中的 24 条是"目标法名已进 top-15 但条号未浮上来"，可对已召回法律做法内二次精排
4. **LexEval 类外部集**: LawBench 可作为外部补充，但需对齐知识库版本，收益有限
