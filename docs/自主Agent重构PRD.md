# 法律智能问答系统重构 PRD —— 从固定管线 RAG 到自主 Agent

| 项目 | 内容 |
| :--- | :--- |
| 文档版本 | v0.1（待评审） |
| 编写日期 | 2026-08-12 |
| 适用系统 | Law-RAG-Agent（法律 RAG 智能问答系统） |
| 重构目标 | 固定管线 → 工具调用型自主 Agent，预留多 Agent 规划升级空间 |
| 评审角色 | 产品 / 技术负责人 / 前端 / 测试 |

## 1. 背景与问题

### 1.1 现状

当前系统是一套**固定管线 RAG**：

```
intent → FAQ缓存 → memory_retrieve → retrieve → generate → validate(失败重试)
```

- 检索组件齐备：pgvector 向量检索 + BM25 混合检索 + bge-reranker 精排
- LLM 双后端工厂：Ollama（本地，当前默认）与 OpenAI 兼容 API（可切 DeepSeek）
- 基于 LangGraph 1.2 编排，但**节点为固定顺序，无工具调用、无 ReAct 循环**
- **无网络搜索能力**，系统提示词明确声明"不具备实时信息查询能力"

### 1.2 核心问题

| # | 问题 | 影响 |
| :--- | :--- | :--- |
| P1 | 无法回答需要实时/最新信息的法律问题（新法规、最新司法解释） | 答案时效性不足 |
| P2 | 查询链路固定，无法按问题类型自适应调整策略 | 简单问题过度检索，复杂问题检索不足 |
| P3 | 检索范围限于内部库，无外部线索发现能力 | 覆盖度受限，案例缺失 |
| P4 | 无执行过程透明化 | 用户无法感知答案来源，信任度低 |

### 1.3 重构目标

将系统升级为**自主 Agent**：能够自主决定调用哪些工具（内部检索 / 通用网络搜索 / 法律权威源验证），按需规划执行路径，并在关键场景（文书/合同/报告类）加入人工确认环节。

## 2. 已确认的关键决策

| # | 决策点 | 结论 |
| :--- | :--- | :--- |
| 1 | 模型接入 | **双后端保留**：外接 API（DeepSeek）为主，Ollama 本地为降级后端 |
| 2 | Agent 形态 | **先工具后规划**：先实现工具调用型（M1），架构预留多 Agent 升级（M3） |
| 3 | 通用搜索 API | **Tavily**，Key 由后端统一管理，存宿主 `.env`，经 docker-compose 注入容器 |
| 4 | 法律垂直源 | 官方免费库（国家法律法规数据库 + 人民法院案例库）为核心 + 小包公等第三方 API 补充案例 + 通用搜索找线索 |
| 5 | 双路冲突 | **内部库优先**；网络信息仅作线索，法律依据必须回源官方库二次验证 |
| 6 | 部署形态 | **本地物理机/VM + Docker Compose** 容器化；pgvector / Redis 容器化，数据挂载宿主机持久化 |
| 7 | 成本控制 | **必须加预算熔断**，日上限 50 元，超阈值自动暂停 |
| 8 | 前端过程展示 | **必须做**：展示"正在调用 XX 工具 / 检索法条"中间过程，基于现有 SSE |

## 3. 目标与非目标

### 3.1 目标

- G1：Agent 能自主编排工具调用，回答含实时信息的问题（最新法规、司法解释、案例）
- G2：双路检索（内部库 + 网络）融合，内部库优先、网络结果回源验证
- G3：分场景自主度——问答类全自动，文书/报告类关键步骤人工确认
- G4：执行过程通过 SSE 实时透明化展示
- G5：预算熔断机制，控制 DeepSeek / Tavily API 费用
- G6：架构预留多 Agent 任务规划能力（M3）

### 3.2 非目标（本期不做）

- 不重构前端框架（继续 Vue3 + Vite）
- 不做多 Agent 任务规划（M3 预留，本期不实现）
- 不更换检索底层存储（继续 pgvector + Redis）
- 不接 Dify / Coze 等外部 Agent 平台

## 6. 系统流程说明

### 6.1 主流程（工具调用型 Agent）

```
用户提问
   │
   ▼
intent 识别 ──► 场景分类（A类 / B类）
   │
   ▼
ReAct 循环（LLM 自主决策，最多 N 轮）：
   ├── 调用 retrieve_knowledge（内部库）
   ├── 调用 web_search（Tavily 通用搜索）
   ├── 调用 legal_source_search（权威源验证 / 补充）
   └── 产出最终答案
   │
   ▼
[B 类场景] 关键步骤确认（human-in-the-loop，SSE 推送给前端）
   │
   ▼
引用溯源校验（幻觉守卫 + 来源标注）
   │
   ▼
SSE 流式输出最终答案
```

### 6.2 双路融合与冲突裁决规则

1. **并行执行**：内部库检索与网络搜索并行发起
2. **融合去重**：合并结果，按来源类型 + 相关度打分排序
3. **冲突裁决**：
   - 内部库数据（经校验的权威数据）**优先级最高**，直接采用
   - 网络结果**仅作线索**，不得直接作为最终法律依据
   - 若网络信息可能更新了法规，必须回源 `legal_source_search` 官方库**二次验证**后才可使用
4. **来源标注**：最终答案中每个法律依据携带来源（内部库 / 官方源 / 网络验证状态）

### 6.3 成本熔断流程

```
每次调用 API 后记录用量（DeepSeek token + Tavily 次数）
   │
   ▼
当日累计费用 > 阈值（默认 50 元）
   │
   ▼
暂停新增 Agent 请求（读模式保留） → 通知管理员 → 管理员调整阈值或续费后恢复
```

## 7. 需求描述（EARS 原则）

### 7.1 Ubiquitous（系统始终满足）

- REQ-U1：系统应始终通过 OpenAI 兼容接口调用外接 API 作为默认模型后端，并在该后端不可用时降级到 Ollama 本地后端。
- REQ-U2：系统应始终为 Agent 可调用的每个工具维护完整的 schema 与描述，供 LLM 路由决策。
- REQ-U3：系统应始终将内部 pgvector 知识库数据视为最高优先级法律依据来源。

### 7.2 Event-driven（事件触发）

- REQ-E1：当用户发起提问时，系统应先执行意图识别与场景分类，再进入 Agent 工具编排流程。
- REQ-E2：当 LLM 决策调用某个工具时，系统应执行该工具并通过 SSE 向前端推送"正在调用 XX 工具"的过程事件。
- REQ-E3：当当日 API 累计费用超过阈值时，系统应暂停新增 Agent 请求并通知管理员。
- REQ-E4：当检测到网络结果涉及法规条文时，系统应回源官方数据库进行二次验证。

### 7.3 Unwanted（异常/故障处理）

- REQ-UW1：如果 Tavily 搜索失败或超时，则系统应记录错误并在结果中标注"搜索不可用"，同时仅基于内部库继续回答。
- REQ-UW2：如果 DeepSeek API 调用失败，则系统应自动切换 Ollama 本地后端并提示用户当前使用降级模型。
- REQ-UW3：如果网络信息与内部库冲突且无法回源验证，则系统应优先内部库，并明确告知用户该信息未经官方验证。
- REQ-UW4：如果 Agent 工具调用达到最大轮数（默认 N=5）仍未产出答案，则系统应停止循环并基于已有信息生成答案或提示用户。

### 7.4 State-driven（状态相关）

- REQ-S1：在 B 类场景（文书/合同/报告类）的确认等待状态下，系统应保持会话挂起，不继续执行后续节点，直至收到用户确认或超时。
- REQ-S2：在预算熔断生效状态下，系统应拒绝新的 Agent 请求，仅允许已授权的读操作。

### 7.5 Optional（可选功能）

- REQ-O1：在用户启用的情况下，系统可将常用检索结果写入 FAQ 缓存以减少 API 调用。
- REQ-O2：在配置了小包公 API 的情况下，系统可将第三方案例检索作为案例补充来源。

## 8. 交互说明（前端）

- **过程透明面板**：对话流中内嵌 Agent 执行过程卡片，展示：当前调用的工具、检索到的法条/案例摘要、来源标签
- **确认交互**：B 类场景在关键步骤前弹出确认卡片（"即将生成合同审查意见，确认审查范围？"），用户确认/修改后继续，SSE 保持连接
- **引用溯源**：最终答案中法条引用可点击，展示来源与验证状态（内部库 / 官方源已验证 / 网络未验证）
- **费用提示**：熔断暂停时前端展示明确提示并引导联系管理员

## 9. 数据指标

| 指标 | 定义 | 目标 |
| :--- | :--- | :--- |
| 工具调用成功率 | 工具调用成功 / 总调用次数 | ≥ 95% |
| 平均工具调用轮数 | 每次问答 Agent 调用工具的平均次数 | ≤ 3 轮 |
| 答案时效性满意度 | 含实时信息问题的答案准确率（抽样） | ≥ 80% |
| 引用可溯源率 | 带来源标注的答案 / 总答案 | 100% |
| 单次问答平均成本 | DeepSeek + Tavily 费用 / 问答次数 | ≤ 0.5 元 |
| 熔断触发准确率 | 触发暂停时实际费用超阈值比例 | 100% |
| B 类场景确认完成率 | 确认后完成 / 发起确认次数 | ≥ 90% |

## 10. 验收标准

- AC-1：用户提问"《民事诉讼法》最新修订内容"，Agent 能通过搜索发现最新修订并回源官方库验证后回答，引用标注验证状态。
- AC-2：Tavily 服务不可用时，系统仍能基于内部库完成回答，并在前端标注"搜索不可用"。
- AC-3：B 类场景（如合同审查），系统在生成意见前发起确认，未确认不产出最终文书。
- AC-4：模拟当日费用超阈值，系统自动暂停新增请求，管理员收到通知，恢复后服务正常。
- AC-5：全程 SSE 流式输出工具调用过程，前端可见"正在调用 XX 工具"事件。
- AC-6：DeepSeek API 失败时自动降级 Ollama，前端提示降级状态。
- AC-7：所有接口保持向后兼容，现有 RAG 问答功能回归通过。

## 12. 风险清单

| 风险 | 等级 | 应对 |
| :--- | :--- | :--- |
| 裁判文书公开接口受限，案例覆盖不足 | 高 | 混合架构：小包公第三方 API 补充 + 通用搜索找线索 + 官方案例库为准 |
| DeepSeek function calling 偶发不稳定 | 中 | 重试机制（已有 `retry.py`）+ 最大轮数限制 + 降级路径 |
| 网络搜索结果质量参差 | 中 | 回源验证机制 + 来源标注 + 幻觉守卫 |
| 多轮工具调用成本不可控 | 中 | 预算熔断 + FAQ 缓存 + 轮数上限 |
| 法律数据合规风险 | 低 | 本地部署、数据主权可控，满足《数据安全法》 |
