## 1. 手法

每档（长度 L）、每个重复，**独立起进程**，保证「冷」是真的冷：

| 步 | 动作 | 取什么 |
| :--- | :--- | :--- |
| 1 | 起进程 → 送 **L 个 token 的数组 prompt**、`n_predict=1` | `prompt_ms` = **冷 prefill** |
| 2 | 记显存 → `save` | `n_saved` / `n_written` |
| 3 | **杀进程** → 重启 → `restore` | `restore_ms` |
| 4 | 追一刀：重发同一 prompt | `cache_n` 应 ≈ `n_saved`、`prompt_ms` 应 ≈ 0 |

**参数**：`-c 16384`、`-ngl 99`、`seed=42`、`temperature=0`、`n_predict=1`、每档 **3 次取中位数**。

> 取 16384 是为了装下最大档 8K。实测**没有触发缩档**，四档全部跑完。

**两次「冷」的证明**（这是最容易放水的地方）：

- 冷 prefill 的 `cache_n` **每一条样本都是 0**（12/12）→ 确实是空缓存起算；
- 暖 prefill 的 `cache_n` **精确等于 L-1**（1023 / 2047 / 4095 / 8191）→ restore 的 KV 被完整复用。

## 2. AC2 · restore 提速

中位数口径，每档 3 次：

| 长度 | 冷 prefill (ms) | restore (ms) | **提速** | 暖 prefill (ms) | 暖/冷 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1024 | 761.2 | 90.9 | **8.38×** | 41.5 | 18.4× |
| 2048 | 1397.6 | 127.6 | **10.95×** | 42.9 | 32.5× |
| **4096** | **2552.1** | **280.5** | **9.10×** | 50.6 | 50.4× |
| 8192 | 4446.7 | 542.1 | **8.20×** | 58.8 | 75.6× |

> **AC2 判据（4K 量级 ≥5×）：9.10× —— 通过。**

**每一条原始样本**（票面要求，不只留中位数）：

| 长度 | 冷 prefill 三次 (ms) | restore 三次 (ms) | save 三次 (ms) |
| ---: | :--- | :--- | :--- |
| 1024 | 748.3 / 761.2 / 799.4 | 100.5 / 67.3 / 90.9 | 136.6 / 129.6 / 130.1 |
| 2048 | 1402.1 / 1397.6 / 1368.0 | 127.6 / 158.8 / 92.5 | 246.6 / 232.5 / 246.9 |
| 4096 | 2609.9 / 2503.6 / 2552.1 | 199.0 / 280.5 / 286.6 | 413.9 / 528.5 / 465.5 |
| 8192 | 4446.7 / 4569.1 / 4305.9 | 685.7 / 542.1 / 535.7 | 844.8 / 943.4 / 906.2 |

**读图三件事**：

1. **提速倍数在 8~11× 之间，不随长度单调上升。** restore 与冷 prefill 都近似线性增长，
   比值自然趋于常数；2K 档的 10.95× 是 restore 恰好较快的那次，不代表趋势。
2. **`save` 比 `restore` 慢约 1.6~2×**（4K：466 ms vs 281 ms）。写盘比读盘贵，
   这点直接影响 T-10「什么时候落盘」的取舍 —— 落盘不是免费的。
3. **B7：restore 的真正价值是「跨进程存活」，不是「比内存缓存快」。**
   同进程内的暖 prefill 只要 50.6 ms（4K），比 restore 的 280.5 ms 快 5.5×，因为它不需要碰磁盘。
   但暖 prefill **活不过进程退出** —— 这正是本 spike 要解决的那个问题。
   拿 restore 和「同进程缓存」比是比错了对手；它的对手是**冷 prefill**。

## 3. AC3 · KV 体积线性

### 3.1 拟合结果

```
bytes = 36880 × tokens + 908
R² = 1.000000        最大预测误差 = 0.0000%
```

四个测点（去重后 4 个，`n_written` 是 `n_saved` 的确定性函数，残差**全部为 0**）：

| tokens (`n_saved`) | 实测字节 | 拟合预测 | 误差 |
| ---: | ---: | ---: | ---: |
| 1024 | 37,766,028 | 37,766,028 | 0 |
| 2048 | 75,531,148 | 75,531,148 | 0 |
| 4096 | 151,061,388 | 151,061,388 | 0 |
| 8192 | 302,121,868 | 302,121,868 | 0 |

> **AC3 判据（R²>0.95、误差<20%）：通过，且是精确线性。**

### 3.2 实测 `bytes/token` 与理论值对账

**不靠印象，直接读 GGUF 头**（`read_gguf_metadata`，原始键值见报告 JSON）：

| GGUF 键 | 值 |
| :--- | :--- |
| `general.architecture` | `qwen2` |
| `qwen2.block_count` | **36** |
| `qwen2.attention.head_count` | 16 |
| `qwen2.attention.head_count_kv` | **2**（GQA） |
| `qwen2.embedding_length` | 2048 |
| `qwen2.context_length` | 32768 |
| `general.file_type` | 15（Q4_K_M） |

**每 token KV 元素数** = `n_layer × (n_kv_head × head_k + n_kv_head × head_v)`

- `head_dim` 由 `embedding_length / head_count` = 2048 / 16 = **128**（GGUF 未直接给 key/value_length）
- = 36 × (2×128 + 2×128) = **18,432 元素**
- 默认 KV 精度 f16 → ×2 字节 = **36,864 B/token**

| | 值 |
| :--- | ---: |
| 实测（`n_written / n_saved` 的中位数） | **36,880.3 B/token** |
| 理论（GGUF 架构公式） | **36,864 B/token** |
| 偏差 | **+16.3 B（+0.044%）** |

**偏差来源解释**（票面要求）：

- **+908 字节的文件头**是主因。拟合截距 908 B ≈ GGUF/KV 文件头的元数据（张量名、形状、对齐填充）。
  按 1024 token 摊，就是 **+0.89 B/token**；按 8192 token 摊只有 **+0.11 B/token** ——
  **故 `bytes/token` 不是常数，token 越少它越大**。`36,880` 这个数只在千 token 量级成立，
  短序列（几十 token）会明显偏离。
- 余下 **+16 B/token** 的斜率偏差（+0.043%）与**对齐/填充**一致：每层 K/V 张量在文件里按
  block 对齐存储，18,432 个 f16 元素的理论值 36,864 B 未含对齐余量。
- **不要混淆**：这里量的是 `--slot-save-path` 落盘的 **`.bin` 文件**大小，
  与运行时显存占用不是一回事（见 §4）。

### 3.3 与 SPEC §9.2 / 附录 §10 第三方参考的对照

SPEC 附录 §10 引的是第三方实测：**27B 模型 4K token → save 211 ms / 219 MB、restore 87 ms，冷 prefill 十几秒 → 7×**。
我们这次是 **3B 模型 4K token → save 466 ms / 151 MB、restore 281 ms、冷 prefill 2.55 s → 9.1×**。

**差异来源（逐条说明，不拿别人的数字充数）**：

| 维度 | 差异 | 原因 |
| :--- | :--- | :--- |
| 体积 | 219 MB vs 151 MB | 模型不同。KV 体积只取决于 `层数 × kv_head × head_dim × 精度`，与参数量不是线性关系。27B 的层数/维度和 3B 不同 |
| restore 绝对耗时 | 87 ms vs 281 ms | **单位字节的读性能差 ~5×**（对方 2.5 GB/s，我们 0.54 GB/s）。这是磁盘/文件系统差异，不是引擎差异 |
| 冷 prefill | 十几秒 vs 2.55 s | 对方算的应是长上下文整段；且 27B 在同类硬件上前向本就慢得多 |
| 提速倍数 | 7× vs 9.1× | 我们的**冷 prefill 相对更慢**（笔记本 GPU 上 3B 每 token 前向占比高），把倍数抬了上去 |
| 上下文 | 未标注 vs `-c 16384` | 我们的冷 prefill 含 16384 容量下的 KV 分配路径 |

> **口径提示**：跨报告的「提速倍数」不可直接比 —— 它同时被模型、硬件、磁盘和基线口径影响。
> 唯一可靠的比法是看**同一台机上** restore 与冷 prefill 的比值，也就是上表。

## 4. 显存账

| 状态 | 显存占用 |
| :--- | ---: |
| 空载（GPU 上还有别的占用） | 1162 MiB |
| 加载 3B Q4_K_M + `-c 16384` 后稳定态 | **~3750 MiB** |
| 净增（模型 + KV） | **≈ 2588 MiB** |

**关键观察（B6）：显存占用与「实际填了多少 token」无关。**
四档的 `gpu_after_prefill` 分别是 3773 / 3780 / 3773 / 3751 MiB —— **8K 档并不比 1K 档多占**。
因为 llama.cpp 在加载时就按 `-c` **预分配整块 KV**。

**这条直接约束 T-14 的叙事，不要写错**：

- 把 KV 落盘**省的是 prefill 时间与计算**，**并没有省显存**；
- 想让落盘也省显存，需要配合「小 `-c` + 频繁 save/restore」的策略，而每次 restore 要花 90~540 ms
  —— 这是笔要单独算的账（见 §5 给 T-11 的数字）。
- SPEC §9.2 提醒「开 embedding/reranker 会额外占用」——本次未启动它们，故**未实测**，
  T-13 汇总时不得把本节数字当成「全套服务」的占用。

## 5. 给下游的数字

**T-11（容量治理）——`KV_MAX_BYTES` 怎么定**

用 `bytes ≈ 36880 × tokens`（万 token 量级下截距可忽略）：

| `KV_MAX_BYTES` | 可容纳 token | 折算成 4K 条目 | 折算成 8K 条目 |
| ---: | ---: | ---: | ---: |
| 256 MB | ≈ 7,276 | ~1.8 | ~0.9 |
| 1 GB | ≈ 29,100 | ~7.1 | ~3.6 |
| 2 GB | ≈ 58,200 | ~14.2 | ~7.1 |
| 4 GB | ≈ 116,400 | ~28.4 | ~14.2 |

- 判据是**磁盘**：`KV_MAX_BYTES` 定的是落盘目录上限，与显存无关（§4）。
- 建议默认 **1 GB**：能放 ~7 条 4K 前缀；按 SPEC 的主场景（ReAct 循环复用同一段
  system + 工具 schema 前缀）条目数本就很少，1 GB 足够宽裕，且不至于让淘汰逻辑形同虚设。
- **注意 `bytes/token` 不是常数**（§3.2）：`n_tokens < 1000` 时截距占比 >3%，
  精确记账要用 `36880 × tokens + 908`，别用单一斜率硬乘。

**T-10（落盘时机）**

`save` 比 `restore` 贵 1.6~2×（4K：466 ms vs 281 ms），且随长度线性增长
（8K 档 save ~900 ms）。**落盘不是免费的**，不宜每次生成都写；
优先在「生成正常结束 / 达到 `max_tokens`」两个点写（与 REQ-E1 一致），且要能异步/懒写。

**T-13（验收套件）**

本脚本可直接复用为 AC2/AC3 的执行体：退出码 0 = 两 AC 全过，报告 JSON 含每条样本。
`--lengths 1024,4096 --repeats 1` 可做快速回归。
