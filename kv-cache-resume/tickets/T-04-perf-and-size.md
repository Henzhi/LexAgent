## 要做出什么

两组数字，都要求可复现、可追溯：

- **AC2**：restore 比冷 prefill 快几倍（4K token 量级要求 ≥5×）
- **AC3**：KV 文件大小对 token 数**线性可预测**（R²>0.95、预测误差<20%）——这是容量治理（T-11）能不能做准的前提

## 范围

**做**

`scripts/04_bench.py`，复用 T-03 的 save/restore 通道：

1. **长度梯度测速**：1K / 2K / 4K / 8K token 上下文（显存不够就缩到能跑的最大档，**并记下缩到哪一档**）
   - 每档分别测 `restore_ms` 与 `cold_prefill_ms`，**各 3 次取中位数**（AC2 判据就是这么定的）
   - 4K 量级的提速倍数单独列出，直接对照 AC2 的 ≥5×
2. **体积采样**：多个 token 数下的 `.bin` 字节数，做线性拟合
   - 输出 R² 与预测误差（AC3）
   - 输出实测 `bytes/token`，与 SPEC §9.2 的估算公式对照，**说明偏差来源**（量化档 / 层数 / KV heads 假设）
3. **显存账**：记录每个档位的实际显存占用（SPEC §9.2 提醒：开 embedding/reranker 会额外占用）

**不做**

- 不做多模型横向对比、不做量化方案对比（SPEC §2.2 非目标）
- 不测并发（spike 定位）

## 验收清单

- [ ] **AC2**：4K 量级 restore vs 冷 prefill ≥ **5× 提速**（中位数口径，报告写明是几次的中位数）
- [ ] **AC3**：拟合 **R²>0.95** 且预测误差 **<20%**，报告给出拟合式
- [ ] 报告给出实测 `bytes/token` 并与 §9.2 估算对照，偏差有解释
- [ ] 原始 JSON 保留了**每一条样本**（三次测量都要在），不只留汇总 —— 后面怀疑数字时能回查
- [ ] 报告明确标注「缩档」情况（若 8K 跑不下，写清实际最大档与原因）

## 备注

- 报告里每个数字都要能回答「哪套模型 / 什么量化 / 多少上下文 / 哪一天」——这是本项目的口径纪律，也是作品集叙事里唯一站得住的部分。
- SPEC 附录 §10 的第三方实测参考是 **27B 模型 4K token：save 211ms / 219MB、restore 87ms，对比冷 prefill 十几秒 → 7×**。我们用的是 3B，倍数与绝对耗时都会不一样，**报告要显式说明差异来源，不要直接引用第三方数字充数**。
- 本票数据是 T-11 容量上限默认值的依据（`KV_MAX_BYTES` 定多少合理，看这里）。
