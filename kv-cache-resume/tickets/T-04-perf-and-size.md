## 要做出什么

两组数字，都要求可复现、可追溯：

- **AC2**：restore 比冷 prefill 快几倍（4K token 量级要求 ≥5×）
- **AC3**：KV 文件大小对 token 数**线性可预测**（R²>0.95、预测误差<20%）——这是容量治理（T-11）能不能做准的前提

## 范围

**做**

`scripts/04_bench.py`，复用 T-03 的 save/restore 通道：

1. **长度梯度测速**：1K / 2K / 4K / 8K token 上下文（显存不够就缩到能跑的最大档，**并记下缩到哪一档**）
   - 每档分别测 `restore_ms` 与 `cold_prefill_ms`，**各 3 次取中位数**（AC2 判据就是这么定的）
   - 4K 量级的提速倍数单独列出，直接对照 AC2 的 ≥5×
2. **体积采样**：多个 token 数下的 `.bin` 字节数，做线性拟合
   - 输出 R² 与预测误差（AC3）
   - 输出实测 `bytes/token`，与 SPEC §9.2 的估算公式对照，**说明偏差来源**（量化档 / 层数 / KV heads 假设）
3. **显存账**：记录每个档位的实际显存占用（SPEC §9.2 提醒：开 embedding/reranker 会额外占用）

**不做**

- 不做多模型横向对比、不做量化方案对比（SPEC §2.2 非目标）
- 不测并发（spike 定位）

## 验收清单

- [x] **AC2**：4K 量级 restore vs 冷 prefill ≥ **5× 提速**（中位数口径，报告写明是几次的中位数）
      → **9.10×**（4096 档，**3 次**中位数：冷 prefill 2552.1 ms / restore 280.5 ms）
- [x] **AC3**：拟合 **R²>0.95** 且预测误差 **<20%**，报告给出拟合式
      → `bytes = 36880 × tokens + 908`，**R² = 1.000000**，最大误差 **0.0000%**
- [x] 报告给出实测 `bytes/token` 并与 §9.2 估算对照，偏差有解释
      → 实测 **36,880.3** vs GGUF 架构公式理论 **36,864**，偏差 **+16.3 B（+0.044%）**；
      解释：908 B 文件头（**故 `bytes/token` 不是常数，短序列会偏大**）+ 每层张量 block 对齐余量
- [x] 原始 JSON 保留了**每一条样本**（三次测量都要在），不只留汇总 —— 后面怀疑数字时能回查
      → `reports/ac2-ac3-measurements.json` 含 12 条样本的冷/暖/restore 三次原始耗时、字节数、显存与进程生命周期
- [x] 报告明确标注「缩档」情况（若 8K 跑不下，写清实际最大档与原因）
      → **未缩档**。`-c 16384` 装得下 8K 档，1K/2K/4K/8K 四档全部实测完成

## 实测结论（详见 [`../docs/phase0-ac2-ac3-report.md`](../docs/phase0-ac2-ac3-report.md)）

| 长度 | 冷 prefill (ms) | restore (ms) | 提速 | 暖 prefill (ms) |
| ---: | ---: | ---: | ---: | ---: |
| 1024 | 761.2 | 90.9 | 8.38× | 41.5 |
| 2048 | 1397.6 | 127.6 | 10.95× | 42.9 |
| **4096** | **2552.1** | **280.5** | **9.10×** | 50.6 |
| 8192 | 4446.7 | 542.1 | 8.20× | 58.8 |

- **`bytes = 36880 × tokens + 908`**，R² = 1.000000
- 给 T-11 的容量表：1 GB ≈ 29,100 token ≈ 7 条 4K 条目（建议默认 1 GB，判据是磁盘不是显存）
- 给 T-10 的提醒：`save` 比 `restore` 贵 1.6~2×（4K：466 ms vs 281 ms），**落盘不是免费的**
