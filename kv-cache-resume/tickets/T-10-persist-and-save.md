## 要做出什么

一次生成正常结束后，KV 被落盘、元数据被写入、索引被更新。**落盘失败只告警，生成侧完全无感。**

配合 T-09 的 `lookup`，策略层的最小闭环就通了：第一次请求冷 prefill → 落盘；第二次同键请求 → restore。

## 范围

**做**

- `kv_cache/policy.py`：`persist(tokens, model_id, quant, ...)`
  - **触发条件要写死并明确排除项**（REQ-E1）：
    - ✅ 生成正常结束
    - ✅ 达到 `max_tokens`
    - ❌ 异常中断 / 用户取消 / 上游报错 —— **不落盘**（半截上下文的 KV 复用了会出错误结果，与 REQ-W2 同一条原则）
  - **写入顺序**（T-08 定的方向，必须照做）：`bin` → `meta` → `index`
  - **失败吞掉**（REQ-W3）：`save` / `meta` / `index` 任一环节失败 → `SaveFailed` 被捕获成告警，**不向上抛**
  - **不留半截**：save 失败时要清理已产生的部分产物
  - **重复 save 语义**：同 key 重复落盘 = 覆盖写，`created_at` 保留首次、`hits` **不清零**（写清规则并配测试）
- `tests/test_policy_persist.py`
  - 正常结束 → 落盘（三个文件都在，meta 字段正确）
  - 达 `max_tokens` → 落盘
  - 异常中断 → **不落盘**（断言目录无新文件）
  - save 抛错 / meta 写失败 / index 写失败：三种各一条，全部断言**不抛** + 目录状态一致
  - 中途失败的一致性：在步骤之间注入异常，断言**不产生「index 有、文件无」的状态**（用 monkeypatch 卡在中间步骤）

**不做**

- 不做淘汰（T-11，但要在 `persist` 前留一个 hook 点给 T-11 调水位/上限检查）
- 不做 token 化（输入侧给现成的 token 序列）
- 不做遥测事件本体（T-12）

## 验收清单

- [ ] **REQ-E1**：正常结束与达 `max_tokens` 两种都触发落盘
- [ ] **REQ-E1 反向**：异常中断/取消**不落盘**（有断言，不是靠约定）
- [ ] **REQ-W3**：save / meta / index 任一环节失败，`persist` 不抛，且**告警被记录**（断言日志内容）
- [ ] 写序断言：在中间步骤注入异常，**不产生「index 有、文件无」**的状态
- [ ] 重复 save 同 key 不产生孤儿文件，且 `hits` 不被清零（断言规则生效）
- [ ] 落盘后立即 `lookup` 同键能命中 —— **闭环自测**（本票最有说服力的一条）

## 备注

- **闭环自测是重点**：`persist` 完再 `lookup`，能命中才算真的通了。这条断言比任何字段检查都强。
- 触发条件的「排除项」要多想一步：LexAgent 的 ReAct 循环里，**达到工具轮上限后强制生成的答案**算不算「正常结束」？这里先按「算」处理（它是完整的最终答案），但要在注释里写明判断依据，Phase 3 接入时可能要到 `finish_reason` 去区分。
- 落盘发生在生成结束的**同一请求路径**上，所以本票的性能影响会直接进入用户感知延迟。save 是 IO + 显存拷贝，实测参考是 27B/4K token 约 211ms（SPEC §10）——**如果实测发现 save 拖慢响应，要在这里记录并交给 T-12 量化**，而不是悄悄改成异步了事。
